# Studio Model catalogue operations

## Lifecycle

An appearance configuration produces an opaque deterministic key. The resolver performs an indexed `appearanceKey + version` lookup. A missing record is claimed with a ten-minute lease and at most three automatic attempts, generated by the background worker, validated, hashed, stored, and published atomically. With `STUDIO_MODEL_REQUIRE_HUMAN_APPROVAL=true` (the rollout default), valid output becomes `REVIEW_REQUIRED`; only an admin approval makes it `READY`.

Fallback is a resolver outcome. It never crosses gender, strongly preserves body type, reports appearance differences, and keeps the static legacy model available when catalogue access fails. Review-required, failed, and deprecated records are never exact hits.

## Storage and deduplication

Production objects use `studio-model-assets/<catalogue-version>/<appearance-key>/<content-hash>.*`. Integration objects must use `studio-model-integration/`. Keys contain no user IDs. Originals are normalized PNG; contained, non-cropped thumbnails are WebP and never upscale an undersized original. SHA-256 detects byte-identical content before another upload. Catalogue assets are shared and must not be deleted when a user changes appearance.

## Versioning and provenance

Assets record provider, provider model, prompt version, appearance version, catalogue version, validation version, generation time, and source type without storing prompts or secrets. Increment catalogue version when provider, base clothing, framing, prompt semantics, or material validation policy changes. Increment appearance version when taxonomy semantics change. Previous versions remain auditable and are not returned as current unless explicitly requested.

## Canonical identity references

Generated shared Studio Models use a reviewed canonical face reference selected by `genderPresentation`. Reference portraits live under `assets/studio-model/identity-references/`, outside the public web root. They are server-side generation inputs and must not be exposed as public profile images.

The reference controls recognizable facial geometry only. Explicit appearance controls continue to govern body type, skin tone, undertone, hairstyle, hair texture, hair length, hair color, and height presentation. Personal digital twins and user-uploaded photos never receive a canonical identity reference.

Generation uses the image-edit path with high input fidelity. Validation compares the generated asset with its mapped reference and adds `identityFidelity` to the normal technical and visual checks. Every generated record stores `identityReferenceId` and `identityReferenceVersion` for auditability. Keep human approval enabled because automated identity comparison is a quality gate, not a guarantee.

When replacing a canonical identity:

1. Add a new versioned file; do not overwrite an existing reference.
2. Add the new reference ID and mapping in `lib/studio-model/identity-references.ts`.
3. Increment the identity and generation prompt versions.
4. Generate and review a bounded sample across body, skin, and hair controls.
5. Deprecate superseded catalogue assets rather than mutating their provenance.

## Integration safeguards

Integration requires all of:

```env
STUDIO_MODEL_INTEGRATION_TEST_ENABLED=true
STUDIO_MODEL_INTEGRATION_TEST_PREFIX=studio-model-integration/
MONGODB_URI=mongodb://.../fitpick-integration
```

The guard rejects database names without `test`, `staging`, or `integration`, unsafe prefixes, and missing explicit enablement. Stub mode is the default and consumes no image credit:

```bash
npm run test:studio-model-integration
```

Real-provider mode is bounded to one requested asset and requires explicit cost acknowledgement:

```bash
npm run test:studio-model-integration -- --real-provider --confirm-image-generation-cost
```

Never use production customer records or production database credentials for either mode.

## Inspection and repair

Read-only index inspection:

```bash
npm run studio-model:check-indexes
```

Read-only consistency audit:

```bash
npm run studio-model:audit
```

Legacy definitions are ambiguous because filenames contain only gender and body type. The importer therefore reports them unresolved and never invents skin or hair values:

```bash
npm run import:legacy-studio-models
npm run import:legacy-studio-models -- --limit=20
```

Write mode additionally requires `--confirm-write`, but must not be used until mappings are reviewed.

Approved local assets can be checked without writing:

```bash
npm run studio-model:register -- --config=/safe/appearance.json --image=/safe/model.png --version=v1
```

Registration requires `--write --confirm-write`, validates before upload, rejects an existing ready key, and prints only opaque identifiers.

## Admin review

Authorized administrators use `/admin/studio-model-assets`. Approve moves `REVIEW_REQUIRED` to `READY`; reject moves it to `FAILED`; retry returns failed work to `MISSING`; deprecate preserves the record while excluding it from exact lookup. All API actions independently require server-side admin authorization and confirmation in the UI.

## Production enablement checklist

1. Deploy with generation disabled.
2. Verify MongoDB indexes.
3. Verify S3 prefix permissions.
4. Verify CloudFront delivery for an exact object key.
5. Verify worker health and bounded retries.
6. Run the stubbed integration test against an isolated database and prefix.
7. Run one explicitly confirmed real-provider integration test.
8. Manually review that generated asset.
9. Register a small approved seed catalogue.
10. Keep human approval enabled.
11. Enable generation only for a bounded test cohort.
12. Observe failure rates, cost, fallback differences, and queue leases.
13. Expand gradually.

## Disable and rollback

Set `STUDIO_MODEL_ASSET_GENERATION_ENABLED=false`, restart workers with updated environment, and leave catalogue records intact. The resolver continues using ready catalogue assets and fails open to legacy models. Do not delete shared S3 objects during rollback. Failed or partial records should be inspected with the audit command and repaired or deprecated through admin review.
